# tools/ — Student Onboarding Agent

The create-only tool layer (Step 8). Tools are the only code allowed to ask
the LMS for changes, and only through the LMS adapter interface
(`../adapters/lms/`).

| File | Role |
|---|---|
| `ToolRegistry.js` | Holds tools; enforces the tool contract and access policy |
| `ToolExecutor.js` | The one way to run a tool: lookup → access check → argument validation → execute |
| `onboarding/createStudentTool.js` | `createStudent` |
| `onboarding/assignStudentToClassroomTool.js` | `assignStudentToClassroom` |
| `onboarding/toolSupport.js` | Shared argument checks (forbidden/unknown fields, approved-data match) |
| `onboarding/index.js` | `createOnboardingToolRegistry(schema)`: create-only, locked |

## Tool contract

```js
{
  description: 'what it does, explicitly',
  access: 'create',                    // 'read' | 'create' exist; there is no update/delete
  inputContract: { ... },              // plain-data description of the accepted arguments
  validateInput(input) { return args }, // deterministic; throws ValidationError
  async execute(context, args) { ... },  // gets only validated args + a controlled context
}
```

The registry refuses:

- **Duplicate names.**
- **Missing parts:** `execute`, `validateInput`, `inputContract` or
  `description`.
- **Access levels** other than `read`/`create`, or outside the registry's own
  `allowedAccess`. The onboarding registry allows only `create`.
- **Names that suggest generic infrastructure or mutation:** `sql`, `query`,
  `command`, `exec`, `http`, `fetch`, `database`, `update`, `delete`,
  `remove`, `drop`, `upsert`, `patch`, ... (e.g. `executeSQL`,
  `queryDatabase`, `runQuery`, `arbitraryHTTP`).

Registered tools are frozen, and `lock()` closes the registry. The onboarding
registry is locked, so no tool can be defined at runtime; tool definitions
exist only in code.

## Onboarding tools

| Tool | Access | Arguments | Calls |
|---|---|---|---|
| `createStudent` | create | `{ rowNumber, student }`. `student` holds only the schema's creation fields: every import field not flagged `classroomAssignment` (`fullName`, `email`, `parentName`, `phone`, `dob`, `admissionDate`, `bloodGroup`, `address`) | `lms.createStudent` |
| `assignStudentToClassroom` | create | `{ rowNumber, email, className, section }`, all required | `lms.assignStudentToClassroom` |

Argument validation is deterministic and reuses the schema and the Step 5
rules rather than duplicating them:

- **Rejected, never silently dropped:**
  - system-controlled fields, matched in any spelling and including aliases:
    `id`, `userId`, `studentId`, `password`, `role`, `isApproved`,
    `universityId`, `classroomId`, `fees`/`totalFees`/…, `status`,
    `createdAt`/`updatedAt`, `subscriptionPlan` (`FORBIDDEN_SYSTEM_FIELD`)
  - the other tool's fields (`FIELD_NOT_ALLOWED_FOR_TOOL`)
  - anything else, e.g. `databaseId` or `approved` (`UNKNOWN_FIELD`)
- **Field rules** (required, email, phone, date, blood group, types) come from
  `StudentDataValidator` for `createStudent` and from `formats.js` for the
  classroom tool's email.
- **Approved-data check:** at execution, the arguments must exactly equal the
  approved row they cite (`APPROVED_DATA_MISMATCH`), and the row must belong
  to the approved import (`ROW_NOT_IN_APPROVED_IMPORT`). Even well-formed
  arguments that were not approved cannot reach the adapter.
- **No IDs from callers:** classrooms are identified by `className` +
  `section` only. The adapter resolves them and reports "not found" or
  "ambiguous"; nobody can supply or invent a classroom ID.
- **Idempotency keys** are generated by the server (`jobId:rowNumber:tool`),
  never taken from arguments.

## Execution context

`execute(context, args)` receives a frozen object with only:

- `jobId`
- `approvedRow(rowNumber)`: one frozen approved row
- `idempotencyKey(tool, rowNumber)`
- `lms`: the adapter facade with exactly `createStudent` and
  `assignStudentToClassroom`

It gets no Express request, environment, `process`, filesystem, database
connection or network client.

## ToolExecutor errors

| Code | When |
|---|---|
| `TOOL_NOT_FOUND` | Unknown tool name (including every generic/update/delete name) |
| `TOOL_FORBIDDEN` | Tool's access level not allowed here (e.g. a `read` tool in the create-only executor) |
| `INVALID_TOOL_ARGUMENTS` | `validateInput` failed; `details` lists `{ field, code, message }` |
| `APPROVED_DATA_MISMATCH` / `ROW_NOT_IN_APPROVED_IMPORT` | Arguments are not the approved data |
| `ADAPTER_FAILURE` | The adapter threw `LmsAdapterError` (safe message; its code in `details`) or returned an invalid response |
| `TOOL_EXECUTION_FAILED` | Anything else; generic message, nothing internal |

## Not implemented (by design)

**`createOnboardingToken`** belongs with the verification and email steps. Its
contract is fixed now so those steps cannot widen it:

- It will accept only an approved student's identity and a fixed onboarding
  purpose.
- It will never accept a token value, password, expiry, callback URL or
  recipient.
- Generation, expiry and delivery policy stay system-controlled.

Implementing it now would couple Step 8 to email and the LMS.
